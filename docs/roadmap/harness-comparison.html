Not a ranking. Each harness optimises a different bottleneck, which is why the feature lists overlap on the coding loop and diverge everywhere else.

01

Process and runtime architecture

The four architectures differ more here than anywhere else: per-session process, daemon plus socket clients, one shared server per user, gateway plus channels.

omp

  • One process per session. --mode rpc / rpc-ui turn it into a line-delimited JSON command/response server; acp serves the Agent Client Protocol over stdio. omp://cli-reference.md
  • --profile isolates auth, sessions, settings and caches; --session-dir relocates session storage. omp://cli-reference.md
  • Built as TypeScript plus Rust native crates behind @oh-my-pi/pi-natives. omp://user-facing-packages.md

jcode

  • “The daemon owns sessions, tools, and provider calls. The TUI is a client on a socket, so the server can live anywhere.” docs, Remote use
  • jcode serve plus --socket over SSH forwarding; -C takes a local checkout and --remote-working-dir the absolute remote path where “every tool, git operation, and edit runs”. docs, Local client, remote server
  • Rust. jcode.sh

opencode

  • “OpenCode discovers or starts one shared background server for your user account. Every local OpenCode client connects to that server, which owns sessions, configuration, integrations, permissions, and tool execution.” CLI docs, Background service
  • --standalone runs a private server, --server <url> attaches to a given one; opencode service set disabled true turns the shared service off. same page
  • Session database is SQLite; path printed by opencode debug paths db. same page

hermes

  • Gateway process routing sessions; a documented “one-gateway-for-all-profiles mode” with scope composition and inbound routing. Multiplexing Gateway Internals
  • Session database state.db with a documented recovery path for a corrupt FTS index or file. State DB Recovery
  • Python, embeddable as a library (AIAgent). Python library guide

Providers and authentication

All four support subscription OAuth and plain API keys. What differs is what sits between the model and the session.

omp: roles, not just models

  • --model accepts a role (slow, @slow) or a fuzzy model match; --smol, --slow, --plan set the per-role models; --models a,b,c sets what Ctrl+P cycles. omp://cli-reference.md § Model selection
  • Separate auth-broker credential vault, and auth-gateway: an HTTP forward proxy backed by the broker, or JSON lines on stdio for a parent process with its own credentials. omp://cli-reference.md § Subcommands
  • Provider-side session id and prompt-cache key are explicit flags. same table

jcode: one login per subscription

  • jcode login --provider claude|openai|gemini|copilot|azure|ollama|lmstudio. docs
  • Headless logins: --no-browser prints the auth URL; --print-auth-url now, --callback-url or --auth-code later. docs
  • jcode provider add writes a named profile with --api-key-stdin so the key never lands in shell history; auth-test --all-configured verifies. docs
  • An account router falls back across accounts on usage limits (site screenshot caption). jcode.sh

opencode: providers plus a Console plane

  • Built-in provider list, /connect in the TUI. Intro
  • Console adds organisations: members, SSO, SCIM, budgets, billing. docs index
  • Console also documents running other harnesses against it: Claude Code, Codex, Hermes, Pi, Raycast. index

hermes: portal, pools, fallbacks

  • Nous Portal, OpenRouter, OpenAI, Anthropic, Google, any OpenAI-compatible endpoint. llms.txt header
  • Credential pools rotate multiple keys or OAuth tokens per provider; fallback providers take over when the primary fails. Credential Pools, Fallback Providers
  • Nous Tool Gateway bundles web search, image generation, TTS and cloud browsers behind one OAuth. Tool Gateway
  • Mixture of Agents presets appear as selectable models. MoA

05

Execution, isolation, approval

Four genuinely different answers, and one of them is a design document rather than shipped behaviour.

omp: tiered approval plus hard budgets

  • --approval-mode always-ask | always-ask-cached | write | yolo; --yolo still applies “explicit tool/user policies and provider safety checks”. omp://cli-reference.md § Tools, approvals, and runtime; omp://approval-mode.md
  • --max-cost stops model requests at a spend ceiling and exits with status 3; --warn-cost warns once; --max-time bounds the run. omp://cli-reference.md
  • --no-pty disables PTY bash; --no-lsp disables LSP, formatting and diagnostics. omp://cli-reference.md
  • Secrets never inline in MCP config: each header runs a resolver script that reads a SOPS bundle at connect time. omp://secrets.md

jcode: two tiers, on paper

  • Design doc: tier 1 auto-allowed (local, reversible), tier 2 requires request_permission for anything leaving the sandbox or reaching “another human… no exceptions”. Review arrives by email, SMS, desktop notification, webhook or a TUI widget. SAFETY_SYSTEM.md
  • Header says Status: Design, Updated: 2026-02-08, “Currently the only consumer is ambient mode”. The same doc shows a [safety.rules] block to promote or demote actions. same doc
  • Explicit non-claim: SetSessionEnv “is not a security sandbox or secret-redaction system. The registry does not intentionally log or persist values, but a command can print its environment into tool output”. HARNESS.md

opencode: a real policy language, with its own caveat

  • Ordered rules { action, resource, effect }, last match wins, no match means ask; a multi-resource operation is denied if any resource denies; approvals are once, always (saves a project-scoped allow rule) or reject. Permissions
  • Shell commands pass through a scanner covering Bash, Zsh, POSIX sh and PowerShell; unanalysable syntax “returns a scanner error rather than executing unverified subcommands”. same page
  • Default base policy allows everything, then asks on *.env reads; plan denies edits except under ~/.opencode/plan; title/summary deny all. same page
  • Same page warns: “shell runs with the host user's filesystem, process, and network authority”.
  • Two policy plugins “ignore removals so that a repository cannot switch off policy enforcement”. Plugins

hermes: sandbox as a per-session choice

  • Six built-in terminal backends: local, Docker, SSH, Daytona, Modal, Vercel Sandbox, plus plugin backends such as Singularity. product page, Checkpoints
  • Daytona and Modal are described as serverless-persistent, hibernating when idle. llms.txt
  • Dangerous-command approval, user authorization, container isolation, plus an egress proxy and Docker network allowlisting. Security, Egress isolation
  • Secrets integration includes 1Password, Bitwarden Secrets Manager and a command helper. index

Multi-agent and unattended work

opencode keeps agents in a permission hierarchy, jcode lets them talk to each other, hermes turns them into a roster of bots with a task board, omp steers them live.

jcode: swarm with conflict notice

  • “When agent A edits a file that agent B has read… the server notifies agent B. Agent B can ignore it if it is not relevant, or it can check the diff.” README
  • Agents can “DM just one agent, broadcast to all other agents hosted by the server, or just agents working in that repo”. README
  • Agents spawn their own workers: “turning the main agent into a coordinator and the swarm agents into workers”, headless or headed. README
  • Auto-poke continues when todos remain; goals get a 0–100 hill-climbability rating and low scores trigger pushback to reframe into something measurable. jcode.sh
  • Ambient mode runs on a schedule with its own budget and work branches ([ambient]). docs

opencode: agents as configuration

  • Built-ins: build (full access), plan (read-only, may write plan files under ~/.opencode/plan), general (no subagents), explore (read and search only); hidden compaction, title, summary. Agents
  • Custom agents are Markdown with frontmatter or JSONC entries; modes primary, subagent, all. Agents
  • “Subagents run with fresh context in their own child sessions. They always run in the background: the parent receives a report when a child goes idle.” Agents
  • subagent permission action gates which agents a parent may launch; a child uses its own permissions. Agents

omp: live steering

  • task fans out subagents with their own agent type, optional isolated worktree, and results that can be written back to the running session. omp://tools/task.md
  • Transcripts are addressable: agent://<id> for the latest output, history://<id> for a concise transcript, writes to agent://<id> delivered as a message, agent://all broadcast. omp://eval/agents
  • Async bash jobs and --wait-async keep a print-mode run alive while background jobs finish, each result starting another turn. omp://cli-reference.md § Headless / print mode

hermes: roster, board, cron

  • delegate_task spawns isolated child agents for parallel workstreams. Delegation
  • Kanban: a durable SQLite-backed task board coordinating multiple profiles, with worker lanes. Kanban
  • Bot Mode turns profiles into named bots with their own model, memory, skills, routines and chats, cooperating in group chats via @mentions. Bot Mode
  • Cron in natural language, delivered to any platform. Cron
  • Git worktrees so several agents can work one repository safely. Git Worktrees

09

Sessions, rollback, self-modification

Four different answers to “undo”. omp restores interrupted runs, jcode forks windows, opencode snapshots per model step, hermes snapshots to a shadow git store that is off by default.

omp

  • --restore resumes a session then continues “what its last process left unfinished when it crashed or was killed: the interrupted turn and the subagents it was running”. omp://cli-reference.md
  • --fork copies a saved session into a new one; --export writes HTML. same page
  • Checkpoint and rewind are first-class tools with their own docs. omp://tools/checkpoint.md, omp://tools/rewind.md

jcode

  • Slash commands include /fork (fork into a new window), /transfer (compact context into a fresh handoff session), /compact, /clear, /rewind, /resume. docs, Slash commands
  • Self-dev: “it will start modifying its own source code… edit, build, and test its own source code, then reload its own binary and continue work in your (potentially many) sessions, fully automatically”. README
  • Forks, transfers and swarm children get independent copies of the parent's session env overrides, lost on daemon restart. HARNESS.md

opencode

  • /undo stages a rollback to a message boundary, restores affected files and re-seats the prompt; /redo cancels before you submit. Snapshots
  • Capture is attempted before each model step and when it settles; scope is the session's active directory inside a git worktree, tracked files plus non-ignored untracked up to 2 MiB each. Snapshots
  • Storage is “a separate internal Git object database under its data directory. Snapshot capture does not create commits, move branches, or intentionally change your repository's index.” Snapshots

hermes

  • Checkpoints are opt-in “as of v2”: “most users never use /rollback, and the shadow-store storage is non-trivial over time, so the default is off”. Checkpoints
  • Triggered before write_file/patch and destructive shell commands; one checkpoint per directory per turn; single shared shadow repo at ~/.hermes/checkpoints/store/, real .git untouched. same page
  • /rollback <N> preserves hand edits through an agent-write ledger; --all overrides. same page
  • Container backends get no checkpoints: “file paths belong to the sandbox rather than the host”. same page
  • Sessions: persistence, resume, search, per-platform tracking. Sessions

Refusals and conflicts

do not treat as gaps in the product

Five claims I could not source, with the searches tried, and two places where two official sources disagree.

Refused: unresolved after a real search

  • jcode LSP and jcode sandboxing. Searched site:jcode.sh LSP language server, jcode.sh docs sandbox isolation permission; read docs, HARNESS.md and SAFETY_SYSTEM.md. HARNESS.md documents an MCP client and per-session proxies, no LSP. Next step: grep -ri lsp crates/, or ask the maintainer.
  • opencode memory. The V2 docs index has no memory page; that is not evidence of absence. Persisted state is documented for sessions, snapshots and compaction only. Next step: read packages/opencode/src/session in the repository.
  • opencode LSP in V2. V1 is explicit (V1 LSP page); V2's permissions page says lsp “is not [a] current V2 Core permission action”, which implies a change but not whether language servers survive.
  • omp public documentation. omp:// is the shipped doc set; there is no public URL. License, repository and release channel are unchecked.
  • Why omp's standalone memory CLI defaults to a hermes-named path. omp://user-facing-packages.md gives ~/.hermes/mnemopi/data/mnemopi.db as the store. Unexplained, not guessed at.

Conflicting official sources

  • jcode memory per session. README table says first session 71.3 MB, about 3.3 MB per additional. README. Site says 3.5 MB extra headless and 10.4 MB extra interactive, “Measured: jcode v0.92.14”. jcode.sh. Same vendor, different builds and methods; the headline ratio is the most favourable pairing. Treat every such number as vendor-measured.
  • hermes platform count. “20+ platforms” on the product page versus “21+ … 19 native to the gateway plus IRC and Microsoft Teams via plugins” in llms.txt. Neither matches the enumeration in the messaging overview, which adds LINE, Raft, Webhooks, BlueBubbles and others. The plugin split in llms.txt is the more precise reading.

How to read every cell in this artifact

  • Public doc, source repo or vendor site: linked inline, read this session.
  • omp://…: document shipped with the binary. Official and canonical, not web-linkable.
