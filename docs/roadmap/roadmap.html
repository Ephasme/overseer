overseer · what a good harness needs

Every capability in harness-comparison.md — the same rows used to compare omp, jcode, opencode and hermes — graded on two independent axes: how much a harness needs it, and how much of it overseer already ships. Priority is a judgement about the market, not about this codebase; status is read off the code, with the file and symbol named for every claim.

00

How to read this

Two axes, deliberately orthogonal. A P0 feature can be missing and a P3 feature can already be built.

Priority: why the feature matters at all

  • P0 Without it overseer cannot be someone's daily driver, or its central claim does not hold. Missing P0 is a bug, not a backlog item.
  • P1 Anyone assessing overseer against the incumbents will ask for it. Its absence is a real cost, not a fatal one.
  • P2 Differentiator. Worth building once P0 and P1 hold; each one is a reason to pick overseer over a rival.
  • P3 Optional. Build for a named user or not at all; several are better left unbuilt.

Status: how much is already there

  • FULL Works end to end and a user gets the whole behaviour.
  • PARTIAL Something ships, but a named piece is missing or refuses a realistic case.
  • NONE Not in the code. Named where I looked, never inferred from silence.

Evidence cites the file and the symbol or literal, not a line number: lines rot, names survive a refactor.

The Field column

Four marks, in the order omp · jcode · opencode · hermes, copied from the comparison doc: ✓ documented by the vendor, ~ partial or caveated, – absent from the docs read. It tells table stakes from differentiators: ✓✓✓✓ is table stakes, –––✓ is one vendor's bet.

What is graded

66 matrix rows from the comparison doc, plus 35 features the second scouting pass surfaced beyond it (hooks, plans, review UX, task environments, trust primitives, MCP client duties) and four harness-engineering items. The matrix's Language row is dropped: it names an implementation choice, not a capability, and overseer's answer is already fixed.

What the shape says

  • Full where it was designed: the tree (spawn, message, control, profiles), the TUI, the offline test suite and the release pipeline are the four places the code is finished rather than started.
  • Partial where a shell substitutes for a tool: read, edit, search and code execution all work through bash and write_file, so a user gets the behaviour while the model pays for it in rounds and tokens.
  • Missing where the harness needs a spine: nothing persists, nothing is counted, nothing is gated. Those three properties cut across nine scopes, which is why the sequence below starts there rather than at any single feature.
  • The matrix flatters breadth and hides this: overseer grades well on the rows a comparison table can express and poorly on the ones that decide whether a week of work survives a crash.

06

Recommended sequence

Ordered by dependency, not by importance: each phase makes the next one cheap, and the first phase is what stops overseer losing work.

PhaseThemeFeaturesWhy here
1Do not lose workState store · Resume · Undo of file changes · Session searchEverything else assumes a session is durable. A crash today takes the fleet's history and any un-checkpointed edit with it.
2Bound the fleetCost control · Run bounds · Usage analytics · Approval modelA tree multiplies every call, so an unbounded run is a bill, not a test. Token accounting is the shared prerequisite for three of these four.
3Be a daily driver in a real repoInstruction files · Compaction · Command-line surface · Working directory · DocumentationThe first hour with overseer in someone else's project: its conventions must load, its window must survive a long task, and its README must not lie.
4Reach the fieldMCP project config + importers · LSP · Headless JSON · Programmatic API/ACP · Remote working directoryTable stakes against omp and opencode, and each one is a door into a surface overseer does not have: editor, CI, another tool's config.
5DifferentiateStructured read/edit · todo · Conflict notice · Async jobs · MemoryOnly after the spine exists: these are the rows where the harness can be better than the field rather than merely equal to it.
07

Deliberate non-goals

Rows from the matrix overseer should refuse, with the reason. A roadmap that only adds is not a roadmap.

Desktop, phone and chat surfaces

The matrix's P3 client rows. Each is a frontend to the same core, and the core is not yet worth a second frontend. A programmatic API (P1) buys the same reach for a tenth of the work.

Self-modification

jcode's one unique row. An agent that rebuilds and restarts its own binary makes every bug a moving target; the value it delivers is a faster development loop for the harness author, not for the user.

Debugger (DAP) and binary RE

omp-only rows. Both are whole subsystems with a narrow audience; a user who needs them has omp.

Media generation and desktop automation

Not a coding capability. The one piece worth having is image input, and that is an LLM-payload fix, not a tool.

Plugin distribution and org policy

Both presuppose a plugin surface and a policy layer that do not exist. Building the registry first would be building the shop before the goods.

Benchmarking

A score for the maintainer, not the user. The behavioural test suite already gates what a release may break.
